## Build / test

- `./gradlew assembleDebug` (build), `./gradlew testDebugUnitTest` (unit tests), `./gradlew lintDebug` (lint). All three are green as of v1.
- No system Java/Android SDK: the toolchain lives in `~/.lumi-dev` — export `JAVA_HOME=~/.lumi-dev/jdk` (JDK 17) and the SDK is at `~/.lumi-dev/android-sdk` (platform 35, build-tools 35.0.0); `local.properties` already points `sdk.dir` there.

## Sharp edges

- NFC is always listening: in both play modes `MainActivity.reconfigureNfc` runs `NfcAdapter` foreground dispatch (self PendingIntent → `onNewIntent` → `handleNfcIntent` → `handleTagDetected`), so a tag read starts/switches playback without a tap and overrides a user pause (`PlaybackPolicy.onTagDetected(uid, paused)` → `NfcAction.Resume` → `PlayerService.ACTION_RESUME`). Do NOT "improve" this back to reader mode: on the real device `onTagDiscovered` never fired where foreground dispatch demonstrably works (tag registration always used it), so foreground dispatch is the single proven receive path. Proximity mode also runs a continuous-reading FAST PATH for tag-lost (captain-approved, no reader mode): the delivered `Tag` handle is held (`lastSeenTag`) and, while it is the active tag, a background coroutine reads page 0 every 300ms (`nfc/MifarePresencePoller.kt`, two-strike debounce: a failed read retries once after 100ms; two failures confirm the removal, pause via the same `handleTagLost` route, and clear the presence record so the fallback doesn't double-report); every successful read refreshes the presence record so the absence-timeout fallback stays quiet while the tag answers. Tags without a Mifare Ultralight session (not ML, or `connect()` fails) fall through to the GENERIC fast path: a connected tag-tech session (NfcA, then IsoDep, then ML; `MainActivity.establishGenericPresenceSession` seam) probed every 300ms by `nfc/GenericPresencePoller.kt` - the probe is a REAL low-level read (NfcA transceive CTX, IsoDep APDU, ML page 0) that only succeeds while the tag is physically in the field, so every successful probe refreshes the presence record and a non-Mifare tag HELD STATIONARY no longer false-pauses after the re-read window (the bug that motivated it: foreground dispatch delivers a stationary tag once, so without a live session the fallback watcher saw "no further reports" and paused). Do NOT reintroduce a `TagTechnology.isConnected` presence check: that is a local connection flag that stays true after the tag leaves the field (it is only cleared by `close()`, which here only happens on cancellation), so an isConnected-polling loop can never detect a physical removal and a removed tag would keep playing forever - the removal signal is a probe that fails twice in a row (100ms retry, the same two-strike debounce as the Mifare path), confirming the removal through the same `handleTagLost` route and clearing the record so the fallback doesn't double-report; a cancelled loop (tag switch / mode change / playback stop) closes the session via `finally` WITHOUT reporting loss. Only when neither session can connect does the absence-timeout fallback own the tag. A new tag presentation or a playback stop cancels whichever loop runs. Known on-device risk: a held-still tag can go cold under foreground dispatch, so the Mifare fast-path read can fail (two-strike debounce covers blips) or the generic fast-path probes can fail twice, pausing before a real removal - on-device validation item. Pinned by `MifarePresencePollerTest` (pure loop/debounce, fake read + fake clock), `GenericPresencePollerTest` (pure loop/debounce, fake probe + fake clock) and `MifarePresencePollUiTest` / `GenericPresencePollUiTest` (Robolectric wiring; the `establishPresenceSession` / `establishGenericPresenceSession` seams are replaced reflectively with fake `PresenceReader`s / `GenericPresenceSession`s - the synthetic tags carry no tech list, so the default factories find no ML and exercise the fallback). Tag intents are consumed after handling (EXTRA_TAG removed) so a stale tag is not reprocessed on a later resume.
- The manifest `TECH_DISCOVERED` filter is dead without its `android.nfc.action.TECH_DISCOVERED` tech-list meta-data (`res/values/nfc_tech_list.xml`); the framework silently skips such filters, so keep both in sync. That intent path only matters for tags tapped while the app is closed (foreground dispatch wins while the app is in the foreground); the always-listening path is foreground dispatch, not this filter.
- Main-page NFC behavior is pinned by `NfcAlwaysListeningUiTest` (Robolectric): it delivers tags as `EXTRA_TAG` intents via `ActivityController.newIntent` — the same shape the system's foreground dispatch delivers — driving the real `onNewIntent` path with reflectively-built `Tag`s (the stub SDK's `Tag` constructor throws and omits the test hooks), and records dispatch state in `NfcTestState` via `ShadowNfcAdapterForTest`.
- Proximity "tag removed" is derived, not reported: there is no tag-lost callback and foreground dispatch may deliver a stationary tag only once per presentation, so the presence poll (ticks every `PRESENCE_CHECK_MS` = 1s in `ui/MainActivity.kt`; the absence window is the user-configurable "Tag re-read wait" setting - `nfc_reread_seconds` in the Room settings table, default 15s, clamped 1-120, persisted like play mode via `LumiRepository.observeNfcRereadSeconds` - and only an absence of reports on the ACTIVE tag longer than that counts as removal; `MainActivity.presenceTimeoutMs()` reads the view model's `nfcRereadSeconds` StateFlow each tick) is posted only in proximity mode — continuous mode keeps playing after the tag leaves. "No further reports" is the only signal, and a stationary tag goes quiet within the window: it still counts as present only while a re-report (movement/re-presentation) - or a successful continuous fast-path read, see below - refreshes the record within the window; a held-still tag that never re-reports is (correctly or not) removed after the window, and an actual removal takes up to ~window+1s to detect on the fallback (the fast path confirms far earlier when it can run); on-device re-report cadence and pause-on-removal timing are the first on-device validation items. Tag loss PAUSES, it does not stop (`PlaybackPolicy.onTagLost` → `NfcAction.PausePlayback` → idempotent service `ACTION_PAUSE`): the session and the active uid are kept so a re-read of the removed tag RESUMES the paused list ("reading overrides pause"); the tag uid is cleared only when playback itself stops. The poll is torn down when the playback state goes IDLE (the `PlayerStateHolder` collector in `MainActivity` removes it and clears the presence record) and re-armed by the `tagActivated` collector when a tag (re-)becomes active, so no background work survives a stop. The presence record is seeded when a tag BECOMES active (start OR switch) and refreshed by re-reads of the tag already playing. The seed is driven by the view model's `tagActivated` flow (emitted from `LumiViewModel.onTagDetected` at the `StartPlayback` branch, where the new active uid is observable after the Room query and policy switch) because the activating read may be the tag's only report and the policy switch is async - without the seed the poll would have nothing to time out and proximity mode would never pause, including for a tag reached by switching. Entering proximity mode (a play-mode switch, or a resume) re-seeds the record from the carried active uid in `reconfigureNfc`, so a tag already playing before the switch is still watched (and, if its handle is on hand, re-enters the fast path). The activity's `handleTagDetected` refreshes only on the active tag's re-reads and must never touch the record for reads of a different, not-yet-active tag (pinned by `NfcAlwaysListeningUiTest`, including the switch-activation, mode-switch and configured-window cases; the service-side pause semantics are pinned by `PlayerServicePauseTest`).
- FGS type: the SDK-35 stubs expose only `ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` (value 0x2), so the manifest declares `android:foregroundServiceType="mediaPlayback"` and `PlayerService.startForegroundWithNotification` requests that type. Do not "fix" the manifest to a `media` spelling: `media` is not a valid flag for the SDK-35 AAPT (a dual `media | mediaPlayback` spelling fails the build).
- Entry types are extensible: `data/EntryType.kt` keeps `AUDIO`, `VIDEO`, `URL` so existing rows still parse, but the app is audio-only in the UI: `VIDEO`/`URL` are unreachable (no picker options, no `addUrlEntry`), and `PlayerService.loadCurrent` skips non-audio entries (stops if the queue has no audio). `fromStorage` keeps its `AUDIO` fallback for unknown types; new types should preserve it.
- Audio files are picked via SAF; read grants are persisted per file (`LumiViewModel.addFileEntry`). No storage permissions are used. A whole folder can also be added: the Content pane's "Add folder" button uses a separate `OpenDocumentTree` launcher (a different contract than the shared `OpenDocument`, so its own registry key; `TagPickerDispatchUiTest.deliverPick` therefore picks the audio picker out of the registry by its *launched* key, not by being the only non-`activity_rq#` entry) and `LumiViewModel.addFolderEntry` persists the grant on the tree uri, then `data/FolderAudioScan.kt` walks it recursively (`collectAudioFiles`: pre-order depth-first, extension filter `SUPPORTED_AUDIO_EXTENSIONS` = mp3/m4a/aac/flac/wav - the codecs ExoPlayer core decodes; unsupported files skipped) and stores one AUDIO entry per file. Content adds dedupe by payload (the content uri) through `LumiRepository.addEntryUnique`: re-adding a folder, or a folder that contains an already-added file, stores no duplicate rows. Folder listing goes through the `LumiViewModel.folderChildren` seam so Robolectric tests fake the tree. Sharp edges: `DocumentsContract` (SAF) is absent from the stub SDK's `android.jar`, so the document-provider protocol (the `_id`/`_display_name`/`_flags` columns, directory flag value 1, child uri shape `scheme://authority/document/<docId>` built with a fresh `Uri.Builder` so the parent's `:tree` fragment doesn't leak) is written inline as literals in that seam - do NOT "fix" those to `DocumentsContract` references, they don't compile; and the `Folder` icon isn't in the icons-core set (it lives in icons-extended, which the project doesn't depend on), hence the text-only folder button. Added folders are also rescannable: `addFolderEntry` remembers the tree uri in a `folders` Room table (v3, `FolderEntity`, unique on `uri`) and the Content pane's "Folders" section lists each with a "Rescan" button (`LumiViewModel.rescanFolder`) that re-walks the tree (`data/FolderAudioScan.kt` `rescanNewSongs` = `collectAudioFiles` minus the already-stored payloads, so the walk order matches the initial add) and stores only the not-yet-stored files via the same `addEntryUnique` uri/payload dedup - an unchanged folder rescans to nothing ("Nothing new in that folder."). Removing a folder only drops the tracking row (no song delete). Pinned by `FolderAudioScanTest` (the pure rescan walk: new root file, new subfolder file, already-stored skipped, unchanged no-op) and `FolderRescanUiTest` (Robolectric: the Folders affordance + rescan add/no-op, driven through the view model with a fake `folderChildren` tree since the SAF picker can't run).
- Compose: `Modifier.shadow` imports from `androidx.compose.ui.draw` (it ships in the `ui` artifact, not `foundation`); an `androidx.compose.foundation.shadow` import does not resolve. Compose UI test assertions like `assertIsDisplayed`/`assertIsNotDisplayed` are extension functions in `androidx.compose.ui.test` — each one needs its own `import` (a missing import reports as "Unresolved reference", which is easy to misread as a classpath/version problem).
- Playback position remembering (per tag, LRU 3): entity + pure logic (`decideRestore`, `fingerprintOf`, `lruEvictions`) live in `data/PlaybackPosition.kt`; restore is computed in `LumiViewModel.startPlayer` and passed to the service as `EXTRA_START_ENTRY_INDEX`/`EXTRA_START_POSITION_MS` so `ACTION_START` stays synchronous (the service does no DB read on start). The service saves via `TagPositionStore` (on `LumiApp`) every 5s while playing plus on pause/stop, and applies the seek from `pendingSeekMs` on the first `STATE_READY` — media3 1.4.1 has no `onPlayerReady` listener. `queueFingerprint` (per-entry type+payload hash) resets a tag's position when its linked list changes; Room column names are explicit `@ColumnInfo` (Room does not snake_case properties).
- Soft lock (front screen only, UI overlay): logic in `ui/SoftLock.kt` (`TripleTapUnlocker`: a fast triple-tap - 3 taps, each within `UNLOCK_TAP_WINDOW_MS` = 450ms of the previous one; a longer gap resets the count) and `ui/PlayerScreen.kt` (lock button top-right, dimming overlay, pre-lock popup with a persisted "don't show again" checkbox; the unlock-hint copy must keep the "3 times FAST" wording - the window is 450ms - pinned by `SoftLockUiTest`); the setting is the Room settings key `lock_popup_suppressed` (`data/Entities.kt`) - the settings table is generic key/value, so new keys need no migration. The overlay never touches playback (`PlayerStateHolder`/`PlayerService`), so the app keeps working while locked. Tests: `TripleTapUnlockerTest` (pure timing) + `SoftLockUiTest` (Robolectric; the Room write for the setting is async, poll the main looper before asserting). Sharp edge: the default Robolectric screen is 320x470dp and the front screen content overflows the bottom - clipped nodes report empty bounds and aren't "displayed", so UI tests use `assertExists` for bottom controls, and the lock control sits near the top of the screen so test taps can reach it.
- NFC prompt: `MainActivity.refreshNfcState` keeps `showNfcPrompt` in sync with NFC availability — raised on resume / when registration starts with the radio missing or off, and cleared once it is usable again (e.g. after the user enables the radio and returns); the dialog (with an `ACTION_NFC_SETTINGS` button) is rendered in `LumiRoot` so it overlays any screen. Don't move the prompt into `SettingsScreen` — the player screen also needs it.
- Settings navigation (polex-style, `ui/SettingsScreen.kt`): the settings screen is a menu of buttons — one `MenuRow` card per setting (play mode, tag re-read wait, NFC tags, content, tag-to-content) — and clicking a row swaps into that setting's own configuration sub-screen (`SettingsPane` enum; the sub-screens' `Scaffold` content is the old inline sections; the re-read-wait pane is a stepper - `−`/`+` buttons, 1-120 s, default 15 - that persists through `LumiViewModel.setNfcRereadSeconds`). System back must unwind sub-screen → menu → player: the screen registers `BackHandler(enabled = pane != Menu)` so navigation-compose's `NavHost` back handler (default on, 2.7+) still pops settings→player from the menu; don't register an always-on BackHandler here or the player hop dies. The pane state, the menu `ScrollState`, and the dialogs (registration/capture/scan/delete) live at the top of `SettingsScreen`, so leaving for a sub-screen loses nothing. Pinned by `SettingsMenuUiTest` (menu rows + each sub-screen + the re-read stepper round trip; the settings values arrive through an async Room round trip, so pump the main looper - `waitForText` - before asserting) and `SettingsBackNavUiTest` (system back via `activity.onBackPressedDispatcher.onBackPressed()`; `@Config(qualifiers = "w320dp-h300dp")` shrinks the Robolectric screen so the menu genuinely overflows and scroll-position survival is testable). A sub-screen's top bar and section card carry the same title as the menu row that opens it (e.g. "Tag to content", "Tag re-read wait"), so tests click rows before the pane exists and assert sub-screen content by unique copy, and `onNodeWithText` multiplicity assertions must account for the duplicated title.
- Scan-first tag workflow (tag-to-content sub-screen, `ui/SettingsScreen.kt`): the user scans the tag ("Scan a tag to view its song list") or picks a chip, sees that tag's current song list, and adds songs with the "Add song to this tag" button (`LumiViewModel.addSongToTag` → `LumiRepository.addEntryToTag`: persists the SAF grant, then stores the entry and appends it to the end of the tag's ordered link list in one Room transaction - so the read (current list) and the append (new song) can't diverge; a safe no-op returning null if the tag was deleted while the pick was in flight). Both "Add content" (Content pane) and "Add song to this tag" (Link pane) launch the single shared `OpenDocument` launcher at the top of `SettingsScreen` - the pending tag id is `rememberSaveable` and set right before `launch`; do NOT give the Link pane its own `OpenDocument` launcher: same-contract launchers share one request key in the activity result registry, so a second one replaces the shared callback and the Content pane's pick is silently dropped. `LumiViewModel.startTagScan` arms `_scanning`; the next `onTagDetected` settles it: a known tag is selected in the link editor, an unknown tag falls through to the normal registration `capture` (whose save then selects the new tag). No tag write happens and the payload format is unchanged: the song list is associated by UID in the DB (the tag payload is name/mode only), so everything here is app-side state only. Pinned by `LinkScanUiTest`, `TagAddSongUiTest` (Robolectric wiring; `addSongToTag` is driven through the view model with a fake content URI since the SAF picker can't run in Robolectric; the Add button may sit below the viewport on the small test screen, so `assertExists`) and `AddSongToTagTest` (the append logic).
- Tag payload (`application/x-lumi` NDEF record, JSON `{name, mode}`): codec lives in `nfc/LumiTagNdef.kt`. Registration capture (`LumiViewModel.onTagDetected` → `capture`) reads it to prefill the tag dialog's name and play mode; a writable tag (NDEF, not read-only, NDEF area large enough to hold the new message - a write replaces the tag's whole NDEF message, so pre-existing content is not subtracted) additionally offers "Save and write to tag" after form confirmation; the mode records only what the tag was registered with (form prefill on re-read) and saving a tag must NOT change the app's play mode. The stub SDK's NFC API is the classic surface: no `Tag.getNdef()`, no `NdefMessage.getRecord(i)`/`getRecordCount`, no `Ndef.getLength`/`isReadOnly` — use `Ndef.get(tag)`, `message.getRecords()`, `message.toByteArray().size`, and `Ndef.isWritable()` (see the KDoc in `LumiTagNdef`). NFC writes must happen from the foreground while the tag is in range (Android 10+); a tag that left range makes the write fail gracefully (tag is still saved).
