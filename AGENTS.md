## Sharp edges

- NFC is always listening: in both play modes `MainActivity.reconfigureNfc` runs `NfcAdapter` foreground dispatch (self PendingIntent → `onNewIntent` → `handleNfcIntent` → `handleTagDetected`), so a tag read starts/switches playback without a tap and overrides a user pause (`PlaybackPolicy.onTagDetected(uid, paused)` → `NfcAction.Resume` → `PlayerService.ACTION_RESUME`). Do NOT "improve" this back to reader mode: on the real device `onTagDiscovered` never fired where foreground dispatch demonstrably works (tag registration always used it), so foreground dispatch is the single proven receive path. Proximity mode also runs a continuous-reading FAST PATH for tag-lost (captain-approved, no reader mode): the delivered `Tag` handle is held (`lastSeenTag`) and, while it is the active tag, a background coroutine reads page 0 every 300ms (`nfc/MifarePresencePoller.kt`), every read through `nfc/ReconnectingPresenceSession`: a failed read first tries a FRESH session (reconnect through the same `establishPresenceSession` seam, closing the stale session on adoption) and only a read that ALSO fails on the fresh session counts as a removal strike - under foreground dispatch a tag HELD STILL in range goes cold (its RF session drops while the tag stays in the field; a plain read failure would pause a present tag ~500 ms after the activating read, device-proven); two-strike debounce over those strikes (a strike retries once after 100ms; two strikes confirm the removal, pause via the same `handleTagLost` route, and clear the presence record so the fallback doesn't double-report); every successful read refreshes the presence record so the absence-timeout fallback stays quiet while the tag answers. Tags without a Mifare Ultralight session (not ML, or `connect()` fails) fall through to the GENERIC fast path: a connected tag-tech session (NfcA, then IsoDep, then ML; `MainActivity.establishGenericPresenceSession` seam) probed every 300ms by `nfc/GenericPresencePoller.kt`, every probe through the same `ReconnectingPresenceSession` wrapper (a failed probe first tries a fresh `establishGenericPresenceSession` session; only a probe that fails on both counts as a strike) - the probe is a REAL low-level read (NfcA transceive CTX, IsoDep APDU, ML page 0) that only succeeds while the tag is physically in the field AND its session is still alive, so every successful probe refreshes the presence record and a non-Mifare tag HELD STATIONARY no longer false-pauses after the re-read window (the bug that motivated it: foreground dispatch delivers a stationary tag once, so without a live session the fallback watcher saw "no further reports" and paused). Do NOT reintroduce a `TagTechnology.isConnected` presence check: that is a local connection flag that stays true after the tag leaves the field (it is only cleared by `close()`, which here only happens on cancellation), so an isConnected-polling loop can never detect a physical removal and a removed tag would keep playing forever - the removal signal is a probe that fails twice in a row (100ms retry, the same two-strike debounce as the Mifare path), confirming the removal through the same `handleTagLost` route and clearing the record so the fallback doesn't double-report; a cancelled loop (tag switch / mode change / playback stop) closes the session via `finally` WITHOUT reporting loss. Only when neither session can connect does the absence-timeout fallback own the tag. A new tag presentation or a playback stop cancels whichever loop runs. The held-still cold-session case is the fresh-session reconnect above: in the round-4 on-device run a 30 s hold kept playing (the device's tag ran the generic fast path; the Mifare path is Robolectric-validated only) and removal still paused within ~1-2 s. Pinned by `ReconnectingPresenceSessionTest` (pure wrapper: a cold-but-present tag reconnects without a strike, a gone tag throws the strike carrying the original read failure as its cause, and superseded/rejected sessions are closed exactly once), `MifarePresencePollerTest` (pure loop/debounce, fake read + fake clock), `GenericPresencePollerTest` (pure loop/debounce, fake probe + fake clock), `NfcColdSessionReconnectUiTest` (Robolectric: a cold Mifare OR generic session whose reconnects answer keeps playing; a cold session whose reconnects fail still pauses through the two-strike route) and `MifarePresencePollUiTest` / `GenericPresencePollUiTest` (Robolectric wiring; the `establishPresenceSession` / `establishGenericPresenceSession` seams are replaced reflectively with fake `PresenceReader`s / `GenericPresenceSession`s - the synthetic tags carry no tech list, so the default factories find no ML and exercise the fallback). Tag intents are consumed after handling (EXTRA_TAG removed) so a stale tag is not reprocessed on a later resume.
- Tag single-connection-slot conflict (root cause of the on-device "removed tag keeps playing ~80%" bug; fixed, do NOT reintroduce): a `Tag` holds at most ONE connected TagTechnology. `BasicTagTechnology.connect()` succeeds at the binder level, then takes the slot via `Tag.setConnectedTechnology(code)`; when another connection already holds it the setter returns false and connect throws `IOException("Only one TagTechnology can be connected at a time.")` - logcat on the Samsung A52 showed exactly that on EVERY delivery, for BOTH techs (MifareUltralight AND NfcA), so the fast path never came up, the 15 s absence-timeout fallback owned every tag, a HELD tag stopped after ~15 s (violating #39's keeps-while-held), and a removed tag took ~15 s to pause. The on-device trigger: tapping the tag while backgrounded makes the NFC stack RESTART the activity (TAG_DISCOVERED) - `onNewIntent` and `onResume` then each started the presence poll for the same tag within milliseconds, and the second establish's connect hit the slot the first was still releasing (plus the NFC stack's own dispatch connection holds the slot on delivery). Fix, all in `ui/MainActivity.kt`: (1) `releaseExistingTagConnection(tag, holder)` - every default establisher does an UNCONDITIONAL `close()` on a tech instance of the tag BEFORE its own `connect()`: the framework's `close()` has no ownership check (bytecode-verified: unconditionally `setTechnologyDisconnected()` - slot to -1 - plus `INfcTag.reconnect(handle)`), so releasing through ANY tech instance of the tag frees the slot and re-activates the RF session whoever held it, and it is a harmless no-op when the slot is free; (2) `reconfigureNfc` KEEPS a running poll whose uid is still the active tag (`keepRunningPoll`) instead of stop+restart - the restart raced the cancelled loop's async `finally` (the stale session's close, on IO) with the fresh establish's connect; (3) `startPresencePoll` same-uid skip (`presencePollUid` + `presencePollJob?.isActive`), so the onNewIntent half of the restart race (a re-delivery of the tag already being polled) is a no-op. Do NOT "simplify" the keep/skip guards back to an unconditional stop+restart: `onPause` already tears the poll down (correct), so the guards only cover the still-resumed re-configures and the in-restart double-start, which is exactly where the device died. Pinned by `NfcTagTechConflictUiTest`: the conflict on the REAL AOSP bytecode (see the Robolectric NFC entry below - `slotOccupiedByAnotherConnection_connectThrowsTheDeviceConflict` reproduces the exact IOException on Mifare AND NfcA instances; `closeOnAnyTechInstanceReleasesTheSlot_thenConnectAcquiresIt` proves the fix's release step through the real `close` body, then the connect acquires the slot and reads; `slotPrimitives_refuseASecondHolder_andReleaseClears`), plus the app-level race guards through the fake session seams (`proximityMode_tagTapRestartsActivity_...` - the on-device restart shape: pause/stop/resume re-establishes exactly once and the restart's re-delivery must NOT - the establish-count discriminator - then a held tag keeps playing past the 15 s window and a lifted tag pauses within the two-strike debounce with no fallback double-report; `proximityMode_nfcReconfiguredWhilePollRunning_keepsTheRunningPoll` - the keep branch, driven by `LumiViewModel.startTagScan`'s re-configuration; `proximityMode_redeliveryOfThePolledTag_isASkip_notARestart` - the same-uid skip on its own: a re-delivery of the tag whose poll is already running is a no-op - the original job and session survive and the fast path is established exactly once). On-device re-verification with the ACTUAL NTAG215 ("hotel", E731954D - the r1 trials used the Mifare "1" tag) and a fresh install is a flagged captain follow-up: the installed APK has a different signature so it cannot be updated in place (a reinstall would wipe the registered tags/songs + SAF grants); the mechanism is verified at the AOSP-bytecode level (Robolectric API-35 ~= device API-34).
- Robolectric NFC framework sharp edges (API-35 jar `15-robolectric-12650502-i7`; needed to write synthetic-tag tests): the instrumented PUBLIC `BasicTagTechnology.connect`/`close`/`reconnect` are RUNTIME NO-OPS - their instrumented private `$$robo$$` bodies never execute through the public entry (a no-op `connect()` leaves the slot untouched, a no-op `close()` never touches the binder) - while the slot field, `setConnectedTechnology`/`setTechnologyDisconnected`, `checkConnected`, `getTagService`, `transceive` and `readPages` DO run. The real AOSP bodies (the exact device bytecode) execute when invoked DIRECTLY via reflection: `BasicTagTechnology` is not in the pruned stub SDK (resolve it with `Class.forName`), and the body is the private 0-arg void method whose name ends with `$$robo$$android_nfc_tech_BasicTagTechnology$<method>` - filter by the `\$connect` / `\$close` suffix (`reconnect` ends with `\$reconnect`, so the filter is unambiguous). A synthetic tag's `INfcTag` proxy MUST answer `isTagUpToDate` with `true`: `Tag.getTagService()` re-checks it on the binder before every operation, and a null answer NPEs the connect/release path. Tech codes in the `Tag` tech list (from the `get` factories' bytecode, NOT guesses): NfcA = 1, IsoDep = 3 (NOT 2), Mifare Ultralight = 9; a MifareUltralight synthetic tag also needs the NfcA extras bundle (`putShort("sak", 0)`) and a UID starting `0x04`. `android.nfc.TransceiveResult(int, byte[])` has a public constructor; result code 1 makes `getResponseOrThrow()` throw `TagLostException` (an `IOException`). The establisher inside `startPresencePoll` runs on a real IO dispatcher, so a fake-seam establish count lands AFTER the delivery's main-thread handling - pump real time (`Thread.sleep` + `idleMainLooper`) before asserting it. JUnit4 gotcha: `org.junit.Assert.assertNotNull` is VOID - `val x = assertNotNull(msg, expr)` assigns `Unit`, not the value.
- The manifest `TECH_DISCOVERED` filter is dead without its `android.nfc.action.TECH_DISCOVERED` tech-list meta-data (`res/values/nfc_tech_list.xml`); the framework silently skips such filters, so keep both in sync. That intent path only matters for tags tapped while the app is closed (foreground dispatch wins while the app is in the foreground); the always-listening path is foreground dispatch, not this filter.
- Main-page NFC behavior is pinned by `NfcAlwaysListeningUiTest` (Robolectric): it delivers tags as `EXTRA_TAG` intents via `ActivityController.newIntent` — the same shape the system's foreground dispatch delivers — driving the real `onNewIntent` path with reflectively-built `Tag`s (the stub SDK's `Tag` constructor throws and omits the test hooks), and records dispatch state in `NfcTestState` via `ShadowNfcAdapterForTest`.
- Proximity "tag removed" is derived, not reported: there is no tag-lost callback and foreground dispatch may deliver a stationary tag only once per presentation, so the presence poll (ticks every `PRESENCE_CHECK_MS` = 1s in `ui/MainActivity.kt`; the absence window is the "Tag re-read wait" setting - `nfc_reread_seconds` in the Room settings table, default 15s, clamped 1-120, persisted via `LumiRepository.observeNfcRereadSeconds` - which has NO settings UI any more (the menu row and the stepper sub-screen were removed on purpose; the value is set through `LumiViewModel.setNfcRereadSeconds`, which tests use to exercise the configured window) - and only an absence of reports on the ACTIVE tag longer than that counts as removal; `MainActivity.presenceTimeoutMs()` reads the view model's `nfcRereadSeconds` StateFlow each tick) is posted only in proximity mode — continuous mode keeps playing after the tag leaves. "No further reports" is the only signal, and a stationary tag goes quiet within the window: it still counts as present only while a re-report (movement/re-presentation) - or a successful continuous fast-path read, see below - refreshes the record within the window; a held-still tag that never re-reports is (correctly or not) removed after the window, and an actual removal takes up to ~window+1s to detect on the fallback (the fast path confirms far earlier when it can run); on-device re-report cadence and the fallback's pause-on-removal timing remain on-device validation items (the fast-path removal pause is device-verified, see the NFC entry above). Tag loss PAUSES, it does not stop (`PlaybackPolicy.onTagLost` → `NfcAction.PausePlayback` → idempotent service `ACTION_PAUSE`): the session and the active uid are kept so a re-read of the removed tag RESUMES the paused list ("reading overrides pause"); the tag uid is cleared only when playback itself stops. The poll is torn down when the playback state goes IDLE with no active tag (the `PlayerStateHolder` collector in `MainActivity` removes it and clears the presence record) and re-armed by the `tagActivated` collector when a tag (re-)becomes active, so no background work survives a stop. Only IDLE with no active tag is a real stop: `PlayerService.stopPlayback` clears the tag along with the IDLE status, and the transient IDLE that lingers during an `ACTION_START` start-up (the service sets the holder's active tag before ExoPlayer is ready) must NOT be treated as one - treating it as a stop disowns the just-activated tag (a removal then pauses nothing and a re-hold restarts the queue instead of resuming) and tears the poll down mid-hold; pinned by `NfcAlwaysListeningUiTest.proximityMode_serviceStartTransientIdle_disownsNothing_removalPauses_rereadResumes`. The presence record is seeded when a tag BECOMES active (start OR switch) and refreshed by re-reads of the tag already playing. The seed is driven by the view model's `tagActivated` flow (emitted from `LumiViewModel.onTagDetected` at the `StartPlayback` branch, where the new active uid is observable after the Room query and policy switch) because the activating read may be the tag's only report and the policy switch is async - without the seed the poll would have nothing to time out and proximity mode would never pause, including for a tag reached by switching. Entering proximity mode (a play-mode switch, or a resume) re-seeds the record from the carried active uid in `reconfigureNfc`, so a tag already playing before the switch is still watched (and, if its handle is on hand, re-enters the fast path). The activity's `handleTagDetected` refreshes only on the active tag's re-reads and must never touch the record for reads of a different, not-yet-active tag (pinned by `NfcAlwaysListeningUiTest`, including the switch-activation, mode-switch and configured-window cases; the service-side pause semantics are pinned by `PlayerServicePauseTest`).
- FGS type: the SDK-35 stubs expose only `ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` (value 0x2), so the manifest declares `android:foregroundServiceType="mediaPlayback"` and `PlayerService.startForegroundWithNotification` requests that type. Do not "fix" the manifest to a `media` spelling: `media` is not a valid flag for the SDK-35 AAPT (a dual `media | mediaPlayback` spelling fails the build).

Sharp edges: the document-provider protocol (the `document_id`/`_display_name`/`mime_type` columns - the real provider's cursor has NO `_id`/`_mime_type` columns at all, so the pre-fix column read crashed on the first row (device-proven); a row is a directory EXACTLY when `mime_type == vnd.android.document/directory` - `DocumentsContract.Document.MIME_TYPE_DIR` - the `_flags` bit 0 is `FLAG_SUPPORTS_THUMBNAIL` on API 26+, NOT a directory bit, so a flags-based check misreads every subfolder as a file and every thumbnailable file as a subfolder) is read through `DocumentsContract.Document` where the SDK has the constants, so do not "restore" the old `_flags & 1` directory check (it was actively wrong on the real providers, whose directory rows set other bits like `FLAG_DIR_PREFERS_GRID` instead). The SAF permission layer is the strict gate, and the root cause of the original on-device failure: the picker persists a grant on the tree uri (`tree/<treeId>`), and the framework's permission check authorizes ONLY the tree-scoped shapes under that grant - every treeless `document/<docId>(/children)` query against the tree's provider is rejected with `SecurityException: Permission Denial ... requires that you obtain access using ACTION_OPEN_DOCUMENT` (device-proven on Android 14). That denial is what the pre-fix treeless seam hit for EVERY folder: its first query (the label read or the root listing) died and the whole add surfaced as the generic "Couldn't read that folder's songs." The fixed seam lists every folder - the tree's root and each subfolder alike - at the tree-scoped `tree/<treeId>/document/<docId>/children` under the grant's own (stripped) treeId, a folder's node uri being its own tree-scoped document uri `tree/<treeId>/document/<docId>` - NEVER the bare tree uri (the matcher has NO entry for it; refused with `UnsupportedOperationException`), NEVER a `child/...` uri (no matcher entry; refused the same way), and NEVER a treeless `document/` uri (the permission layer denies it under the tree grant). The tree-scoped shapes are matcher-accepted but gated by `enforceTree` (a no-op when docId == treeId, `SecurityException` for a docId outside the tree), which is why every node uri carries the grant's own treeId. A picked tree's docIds contain `/` and `:` (e.g. `primary:Music/Album/song.mp3`), so every uri the seam builds carries the treeId and the docId EACH percent-encoded into ONE path segment (`Uri.encode(id, null)` + `encodedPath`): a file's payload is `scheme://authority/tree/<treeId>/document/<docId>` with EXACTLY four path segments - and the tree-scoped shape is precisely what the tree grant authorizes to OPEN (device-proven: the treeless `document/<docId>` payload the pre-fix seam stored is denied with a SecurityException under the same grant, the tree-scoped one opens). The stub SDK's `DocumentsContract.buildDocumentUriUsingTree` / `buildChildDocumentsUriUsingTree` throw `RuntimeException("Stub!")`, so the seam builds these uris by hand - do not "fix" them to the builder helpers. `collectAudioFiles` also guards a folder that lists itself (visited-set) so a misbuilt child uri can't loop the walk. Read failures are ATTRIBUTABLE: `folderChildrenAttributed` wraps each listing query in a `Log.e(TAG, "Failed to list the children of <uri>", e)` and the add/rescan/removal top levels log their own failing tree uri, so a failure names the folder + exception in logcat (TAG = "LumiViewModel") while the user-facing events stay the pinned generic copy. The root's docId is the picker's tree uri's second path segment (decoded by `Uri.pathSegments`); a picker-appended `:openable` suffix on that segment (android.net.Uri has no `:`-fragment parsing - `Uri.parse` leaves it in the path; no AOSP `DocumentsContract` constant carries a `:tree` OR `:openable` suffix, so the stripping is defensive) is removed before the query - the provider answers only the bare docId. The strip applies to the picker's tree uri ONLY (`treeIdOf` / `folderDocIdOf`): the tree-scoped node uris the seam builds carry the already-stripped treeId as their second segment and the subfolder's docId VERBATIM as their fourth (a subfolder's docId may legitimately end in `:openable` - legal on ext4 - and stripping it there would corrupt a fully readable folder's listing). The picker's tree uri is `content://<authority>/tree/<docId>` (`DocumentsContract.buildTreeDocumentUri`); the folders table stores the picker uri verbatim (normalization is at query time only).
