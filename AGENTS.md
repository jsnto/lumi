## Sharp edges

- NFC is always listening: in both play modes `MainActivity.reconfigureNfc` runs `NfcAdapter` foreground dispatch (self PendingIntent → `onNewIntent` → `handleNfcIntent` → `handleTagDetected`), so a tag read starts/switches playback without a tap and overrides a user pause (`PlaybackPolicy.onTagDetected(uid, paused)` → `NfcAction.Resume` → `PlayerService.ACTION_RESUME`). Do NOT "improve" this back to reader mode: on the real device `onTagDiscovered` never fired where foreground dispatch demonstrably works (tag registration always used it), so foreground dispatch is the single proven receive path. Proximity mode also runs a continuous-reading FAST PATH for tag-lost (captain-approved, no reader mode): the delivered `Tag` handle is held (`lastSeenTag`) and, while it is the active tag, a background coroutine reads page 0 every 300ms (`nfc/MifarePresencePoller.kt`, two-strike debounce: a failed read retries once after 100ms; two failures confirm the removal, pause via the same `handleTagLost` route, and clear the presence record so the fallback doesn't double-report); every successful read refreshes the presence record so the absence-timeout fallback stays quiet while the tag answers. Tags without a Mifare Ultralight session (not ML, or `connect()` fails) fall through to the GENERIC fast path: a connected tag-tech session (NfcA, then IsoDep, then ML; `MainActivity.establishGenericPresenceSession` seam) probed every 300ms by `nfc/GenericPresencePoller.kt` - the probe is a REAL low-level read (NfcA transceive CTX, IsoDep APDU, ML page 0) that only succeeds while the tag is physically in the field, so every successful probe refreshes the presence record and a non-Mifare tag HELD STATIONARY no longer false-pauses after the re-read window (the bug that motivated it: foreground dispatch delivers a stationary tag once, so without a live session the fallback watcher saw "no further reports" and paused). Do NOT reintroduce a `TagTechnology.isConnected` presence check: that is a local connection flag that stays true after the tag leaves the field (it is only cleared by `close()`, which here only happens on cancellation), so an isConnected-polling loop can never detect a physical removal and a removed tag would keep playing forever - the removal signal is a probe that fails twice in a row (100ms retry, the same two-strike debounce as the Mifare path), confirming the removal through the same `handleTagLost` route and clearing the record so the fallback doesn't double-report; a cancelled loop (tag switch / mode change / playback stop) closes the session via `finally` WITHOUT reporting loss. Only when neither session can connect does the absence-timeout fallback own the tag. A new tag presentation or a playback stop cancels whichever loop runs. Known on-device risk: a held-still tag can go cold under foreground dispatch, so the Mifare fast-path read can fail (two-strike debounce covers blips) or the generic fast-path probes can fail twice, pausing before a real removal - on-device validation item. Pinned by `MifarePresencePollerTest` (pure loop/debounce, fake read + fake clock), `GenericPresencePollerTest` (pure loop/debounce, fake probe + fake clock) and `MifarePresencePollUiTest` / `GenericPresencePollUiTest` (Robolectric wiring; the `establishPresenceSession` / `establishGenericPresenceSession` seams are replaced reflectively with fake `PresenceReader`s / `GenericPresenceSession`s - the synthetic tags carry no tech list, so the default factories find no ML and exercise the fallback). Tag intents are consumed after handling (EXTRA_TAG removed) so a stale tag is not reprocessed on a later resume.
- The manifest `TECH_DISCOVERED` filter is dead without its `android.nfc.action.TECH_DISCOVERED` tech-list meta-data (`res/values/nfc_tech_list.xml`); the framework silently skips such filters, so keep both in sync. That intent path only matters for tags tapped while the app is closed (foreground dispatch wins while the app is in the foreground); the always-listening path is foreground dispatch, not this filter.
- Main-page NFC behavior is pinned by `NfcAlwaysListeningUiTest` (Robolectric): it delivers tags as `EXTRA_TAG` intents via `ActivityController.newIntent` — the same shape the system's foreground dispatch delivers — driving the real `onNewIntent` path with reflectively-built `Tag`s (the stub SDK's `Tag` constructor throws and omits the test hooks), and records dispatch state in `NfcTestState` via `ShadowNfcAdapterForTest`.
- Proximity "tag removed" is derived, not reported: there is no tag-lost callback and foreground dispatch may deliver a stationary tag only once per presentation, so the presence poll (ticks every `PRESENCE_CHECK_MS` = 1s in `ui/MainActivity.kt`; the absence window is the "Tag re-read wait" setting - `nfc_reread_seconds` in the Room settings table, default 15s, clamped 1-120, persisted via `LumiRepository.observeNfcRereadSeconds` - which has NO settings UI any more (the menu row and the stepper sub-screen were removed on purpose; the value is set through `LumiViewModel.setNfcRereadSeconds`, which tests use to exercise the configured window) - and only an absence of reports on the ACTIVE tag longer than that counts as removal; `MainActivity.presenceTimeoutMs()` reads the view model's `nfcRereadSeconds` StateFlow each tick) is posted only in proximity mode — continuous mode keeps playing after the tag leaves. "No further reports" is the only signal, and a stationary tag goes quiet within the window: it still counts as present only while a re-report (movement/re-presentation) - or a successful continuous fast-path read, see below - refreshes the record within the window; a held-still tag that never re-reports is (correctly or not) removed after the window, and an actual removal takes up to ~window+1s to detect on the fallback (the fast path confirms far earlier when it can run); on-device re-report cadence and pause-on-removal timing are the first on-device validation items. Tag loss PAUSES, it does not stop (`PlaybackPolicy.onTagLost` → `NfcAction.PausePlayback` → idempotent service `ACTION_PAUSE`): the session and the active uid are kept so a re-read of the removed tag RESUMES the paused list ("reading overrides pause"); the tag uid is cleared only when playback itself stops. The poll is torn down when the playback state goes IDLE (the `PlayerStateHolder` collector in `MainActivity` removes it and clears the presence record) and re-armed by the `tagActivated` collector when a tag (re-)becomes active, so no background work survives a stop. The presence record is seeded when a tag BECOMES active (start OR switch) and refreshed by re-reads of the tag already playing. The seed is driven by the view model's `tagActivated` flow (emitted from `LumiViewModel.onTagDetected` at the `StartPlayback` branch, where the new active uid is observable after the Room query and policy switch) because the activating read may be the tag's only report and the policy switch is async - without the seed the poll would have nothing to time out and proximity mode would never pause, including for a tag reached by switching. Entering proximity mode (a play-mode switch, or a resume) re-seeds the record from the carried active uid in `reconfigureNfc`, so a tag already playing before the switch is still watched (and, if its handle is on hand, re-enters the fast path). The activity's `handleTagDetected` refreshes only on the active tag's re-reads and must never touch the record for reads of a different, not-yet-active tag (pinned by `NfcAlwaysListeningUiTest`, including the switch-activation, mode-switch and configured-window cases; the service-side pause semantics are pinned by `PlayerServicePauseTest`).
- FGS type: the SDK-35 stubs expose only `ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` (value 0x2), so the manifest declares `android:foregroundServiceType="mediaPlayback"` and `PlayerService.startForegroundWithNotification` requests that type. Sharp edges: the document-provider protocol (the `_id`/`_display_name`/`_flags` columns, directory flag value 1) is written inline as literals in that seam - the stub jar once lacked `DocumentsContract` entirely (it was regenerated 2026-09-18 and now carries the full class), so don't treat the literals as stale to "fix" by reflex; the code keeps them. The provider's uri grammar is STRICT and a picked tree's docIds contain `/` and `:` (e.g. `primary:Music/Album/song.mp3`), so every uri the seam builds carries the docId percent-encoded into ONE path segment (`Uri.encode(docId, null)` + `encodedPath`): a file's payload is `scheme://authority/document/<docId>` with EXACTLY two path segments - `Uri.Builder().path("document/$docId")` encodes `:` and spaces but leaves the raw `/`, making a 3-segment uri the device provider refuses with `IllegalArgumentException: Invalid document id`, which is what the on-device .mp3-folder "Couldn't read that folder's songs." actually was (a stored payload would have been a uri the player can't open too); a subfolder's children are listed at the tree's CHILD uri `scheme://authority/child/<treeSeg>:tree/<docId>`, never at the subfolder's document uri (which answers with the folder's own single row, not its children); and querying the tree uri lists the root's children AND the tree's own root row first (`_id` = the tree's own segment, dir flag), which the seam skips - that row's children are the listing's own rows, so recursing into it re-lists the root through an invalid uri (every scan died on that first recursion, even for a flat folder of .mp3 files). `collectAudioFiles` also guards a folder that lists itself (visited-set) so a misbuilt child uri can't loop the walk. Read failures are ATTRIBUTABLE: `folderChildrenAttributed` wraps each listing query in a `Log.e(TAG, "Failed to list the children of <uri>", e)` and the add/rescan/removal top levels log their own failing tree uri, so a failure names the folder + exception in logcat (TAG = "LumiViewModel") while the user-facing events stay the pinned generic copy. The tree uri's `:tree`/`:openable` picker suffix is part of its LAST PATH SEGMENT, not a fragment (android.net.Uri has no `:`-fragment parsing - `Uri.parse` leaves it in the path), so code that parses a tree uri must strip the suffix from the decoded last segment - the seam does exactly that: a trailing ':openable' is stripped from the tree uri before the provider query (the canonical `:tree` shape) and from the last path segment it consumes (treeSeg), so the root-row skip and the child-uri treeId both run on the canonical segment; the ':tree' suffix is never stripped and the folders table stores the picker uri verbatim (normalization is at query time only). And the `Folder` icon IS in the extended set now that `material-icons-extended` is a dependency (see the Compose entry), so folder affordances use icons, not text. The scan-in-progress dialog copy is "Hold the back of the phone against any NFC tag…" (unified behavior: any tag). The settle does a Room query before resolving, so tests must wait on the RESULT (the capture / the detail page), not just the `scanActive` flag flipping. It reuses the read path registration uses (the foreground-dispatch read into `onTagDetected`): there is no new read path. Pinned by `TagScanUiTest` (the button's placement + separation + the absent +; a scan of a registered tag opens the detail page; a scan of an unregistered tag enters registration and saves; the scan settles on the first read so the next read is a playback read; the scan results are driven the way the NFC tests drive tag reads: reflectively-built `Tag`s delivered as `EXTRA_TAG` intents via `ActivityController.newIntent`, the same shape the system's foreground dispatch delivers). The tag detail page's "Add song" and the Content pane's "Add content" launch the single shared `OpenDocument` launcher at the top of `SettingsScreen` - the pending tag id is `rememberSaveable` and set right before `launch`; do NOT add a second `OpenDocument` launcher: same-contract launchers share one request key in the activity result registry, so a second one replaces the shared callback and the other pane's pick is silently dropped (a pick after visiting the detail page must still reach the plain content path - pinned by `TagPickerDispatchUiTest`). `LumiViewModel.addSongToTag` → `LumiRepository.addEntryToTag` persists the SAF grant, then stores the entry and appends it to the end of the tag's ordered link list in one Room transaction (a safe no-op returning null if the tag was deleted while the pick was in flight). The old scan-first link-editor workflow (tag chips, per-entry "+ song" pills, drag reorder) is GONE: songs are managed from the tag detail page only.
- Tag payload (`application/x-lumi` NDEF record, JSON `{name, mode}`): codec lives in `nfc/LumiTagNdef.kt`. Registration capture (`LumiViewModel.onTagDetected` → `capture`) reads it to prefill the tag dialog's name and play mode; a writable tag (NDEF, not read-only, NDEF area large enough to hold the new message - a write replaces the tag's whole NDEF message, so pre-existing content is not subtracted) additionally offers "Save and write to tag" after form confirmation; the mode records only what the tag was registered with (form prefill on re-read) and saving a tag must NOT change the app's play mode. The stub SDK's NFC API is the classic surface: no `Tag.getNdef()`, no `NdefMessage.getRecord(i)`/`getRecordCount`, no `Ndef.getLength`/`isReadOnly` — use `Ndef.get(tag)`, `message.getRecords()`, `message.toByteArray().size`, and `Ndef.isWritable()` (see the KDoc in `LumiTagNdef`). NFC writes must happen from the foreground while the tag is in range (Android 10+); a tag that left range makes the write fail gracefully (tag is still saved).
- Settings-section title-row actions (`ui/SettingsScreen.kt` `SectionCard`): the per-section "+" actions (add content / add folder) sit right-aligned on the section card's TITLE ROW (the NFC tags section has NO + button - its entry point is the "Scan NFC" action button above the tag list, see the tag-scan entry) - `SectionCard` renders the section title as a Row with an optional add button trailing it (its `addLabel`/`onAdd` parameters; the button is a 40 dp peach circle inside the 48 dp `IconButton`, and the `contentDescription` + `clickable` ride the 40 dp circle's own node so the semantics node's bounds are the button's - the geometry tests measure a 40 dp inset flush-right), not pinned to the bottom of the card (that bottom-of-card spot was tried in #25 and felt wrong on-device). The `trailing` parameter renders an extra title-row action at the row's right end (the tag detail page's "Edit tag" `ModeEdit` button). The old standalone "Add folder" text button is gone: it is the + button on the Content pane's Folders section, so tests find it with `onNodeWithContentDescription("Add folder")`, not by text. `onNodeWithText` does NOT match a node's `contentDescription`, so icon-only buttons must be found with `onNodeWithContentDescription`. `PlayModeItemUiTest` pins the header-row placement (title-row vertical centering, flush-right edge, above the section content) for both the Content section's + and the Folders section's +.
