## Build / test

- `./gradlew assembleDebug` (build), `./gradlew testDebugUnitTest` (unit tests), `./gradlew lintDebug` (lint). All three are green as of v1.
- No system Java/Android SDK: the toolchain lives in `~/.lumi-dev` — export `JAVA_HOME=~/.lumi-dev/jdk` (JDK 17) and the SDK is at `~/.lumi-dev/android-sdk` (platform 35, build-tools 35.0.0); `local.properties` already points `sdk.dir` there.

## Sharp edges

- NFC is always listening: in both play modes `MainActivity.reconfigureNfc` runs `NfcAdapter` foreground dispatch (self PendingIntent → `onNewIntent` → `handleNfcIntent` → `handleTagDetected`), so a tag read starts/switches playback without a tap and overrides a user pause (`PlaybackPolicy.onTagDetected(uid, paused)` → `NfcAction.Resume` → `PlayerService.ACTION_RESUME`). Do NOT "improve" this back to reader mode: on the real device `onTagDiscovered` never fired where foreground dispatch demonstrably works (tag registration always used it), so foreground dispatch is the single proven receive path. Tag intents are consumed after handling (EXTRA_TAG removed) so a stale tag is not reprocessed on a later resume.
- The manifest `TECH_DISCOVERED` filter is dead without its `android.nfc.action.TECH_DISCOVERED` tech-list meta-data (`res/values/nfc_tech_list.xml`); the framework silently skips such filters, so keep both in sync. That intent path only matters for tags tapped while the app is closed (foreground dispatch wins while the app is in the foreground); the always-listening path is foreground dispatch, not this filter.
- Main-page NFC behavior is pinned by `NfcAlwaysListeningUiTest` (Robolectric): it delivers tags as `EXTRA_TAG` intents via `ActivityController.newIntent` — the same shape the system's foreground dispatch delivers — driving the real `onNewIntent` path with reflectively-built `Tag`s (the stub SDK's `Tag` constructor throws and omits the test hooks), and records dispatch state in `NfcTestState` via `ShadowNfcAdapterForTest`.
- Proximity "tag removed" is derived, not reported: there is no tag-lost callback and foreground dispatch may deliver a stationary tag only once per presentation, so the presence watcher (`PRESENCE_TIMEOUT_MS` in `ui/MainActivity.kt`) treats a short absence of reports on the ACTIVE tag as removal and is posted only in proximity mode — continuous mode keeps playing after the tag leaves. "No further reports" is the only signal, so a held-still tag may trigger the timeout early; stop-on-removal timing under foreground dispatch is the first on-device validation item. The presence record is seeded when a tag BECOMES active (start OR switch) and refreshed by re-reads of the tag already playing. The seed is driven by the view model's `tagActivated` flow (emitted from `LumiViewModel.onTagDetected` at the `StartPlayback` branch, where the new active uid is observable after the Room query and policy switch) because the activating read may be the tag's only report and the policy switch is async - without the seed the watcher would have nothing to time out and proximity mode would never stop, including for a tag reached by switching. Entering proximity mode (a play-mode switch, or a resume) re-seeds the record from the carried active uid in `reconfigureNfc` (accepted tradeoff: a still-present stationary tag stops after the timeout), so a tag already playing before the switch is still watched. The activity's `handleTagDetected` refreshes only on the active tag's re-reads and must never touch the record for reads of a different, not-yet-active tag (pinned by `NfcAlwaysListeningUiTest`, including the switch-activation and mode-switch cases).
- FGS type: the SDK-35 stubs expose only `ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` (value 0x2), so the manifest declares `android:foregroundServiceType="mediaPlayback"` and `PlayerService.startForegroundWithNotification` requests that type. Do not "fix" the manifest to a `media` spelling: `media` is not a valid flag for the SDK-35 AAPT (a dual `media | mediaPlayback` spelling fails the build).
- Entry types are extensible: `data/EntryType.kt` keeps `AUDIO`, `VIDEO`, `URL` so existing rows still parse, but the app is audio-only in the UI: `VIDEO`/`URL` are unreachable (no picker options, no `addUrlEntry`), and `PlayerService.loadCurrent` skips non-audio entries (stops if the queue has no audio). `fromStorage` keeps its `AUDIO` fallback for unknown types; new types should preserve it.
- Audio files are picked via SAF; read grants are persisted per file (`LumiViewModel.addFileEntry`). No storage permissions are used.
- Compose: `Modifier.shadow` imports from `androidx.compose.ui.draw` (it ships in the `ui` artifact, not `foundation`); an `androidx.compose.foundation.shadow` import does not resolve.
- Playback position remembering (per tag, LRU 3): entity + pure logic (`decideRestore`, `fingerprintOf`, `lruEvictions`) live in `data/PlaybackPosition.kt`; restore is computed in `LumiViewModel.startPlayer` and passed to the service as `EXTRA_START_ENTRY_INDEX`/`EXTRA_START_POSITION_MS` so `ACTION_START` stays synchronous (the service does no DB read on start). The service saves via `TagPositionStore` (on `LumiApp`) every 5s while playing plus on pause/stop, and applies the seek from `pendingSeekMs` on the first `STATE_READY` — media3 1.4.1 has no `onPlayerReady` listener. `queueFingerprint` (per-entry type+payload hash) resets a tag's position when its linked list changes; Room column names are explicit `@ColumnInfo` (Room does not snake_case properties).
- NFC prompt: `MainActivity.refreshNfcState` keeps `showNfcPrompt` in sync with NFC availability — raised on resume / when registration starts with the radio missing or off, and cleared once it is usable again (e.g. after the user enables the radio and returns); the dialog (with an `ACTION_NFC_SETTINGS` button) is rendered in `LumiRoot` so it overlays any screen. Don't move the prompt into `SettingsScreen` — the player screen also needs it.
- Tag payload (`application/x-lumi` NDEF record, JSON `{name, mode}`): codec lives in `nfc/LumiTagNdef.kt`. Registration capture (`LumiViewModel.onTagDetected` → `capture`) reads it to prefill the tag dialog's name and play mode; a writable tag (NDEF, not read-only, NDEF area large enough to hold the new message - a write replaces the tag's whole NDEF message, so pre-existing content is not subtracted) additionally offers "Save and write to tag" after form confirmation, and saving applies the dialog's mode as the app's play mode. The stub SDK's NFC API is the classic surface: no `Tag.getNdef()`, no `NdefMessage.getRecord(i)`/`getRecordCount`, no `Ndef.getLength`/`isReadOnly` — use `Ndef.get(tag)`, `message.getRecords()`, `message.toByteArray().size`, and `Ndef.isWritable()` (see the KDoc in `LumiTagNdef`). NFC writes must happen from the foreground while the tag is in range (Android 10+); a tag that left range makes the write fail gracefully (tag is still saved).
